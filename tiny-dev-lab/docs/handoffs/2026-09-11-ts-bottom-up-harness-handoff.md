## 이 대화의 의미

이번 대화는 tiny-dev-lab의 최종 기획을 확정한 세션이 아니다. TypeScript 파트를 먼저 만들어 보면서, 실제 콘텐츠를 만들 때 어떤 문제가 생기는지 확인한 바텀업 실험에 가깝다.

이 실험을 통해 확인한 핵심은 다음과 같다.

- 기능 구현만으로는 좋은 학습 사이트가 되지 않는다.
- 커리큘럼의 제목, 설명, 스토리, 과제는 반드시 학습 주제에서 출발해야 한다.
- 임의의 예제 함수명이나 상황을 중심에 두면 사용자가 “무엇을 배우는지” 알 수 없다.
- 한국어 문장이 영어 번역투처럼 흐르면 학습 의욕이 크게 떨어진다.
- 각 기술 스택은 “실무에서 겪는 일”과 연결되어야 한다.
- 이 기준은 기억이나 말로만 유지하면 반복해서 무너진다. 스킬 문서와 실행 가능한 하네스가 필요하다.

따라서 다음 대화에서는 이 TS 실험을 기준으로 삼지 말고, 이 실험에서 드러난 실패와 사용자 피드백을 기준으로 탑다운 기획을 다시 잡아야 한다.

## 사용자의 목표

사용자는 지루한 동영상 강의 대신, 짧은 이야기와 실습을 통해 웹 개발 필수 기술을 학습하고 싶어 한다.

대상 기술은 다음을 포함한다.

- TypeScript
- React
- Next.js
- NestJS
- Prisma
- Jest + React Testing Library
- Redis

사이트는 sqlteaching.com처럼 단순한 구조를 참고하되, SQL이 아니라 웹 개발 실무 스택을 다룬다.

기본 학습 흐름은 다음 구조를 가진다.

```text
짧은 이야기 → 핵심 개념 → 직접 코드 수정 → 실행·피드백 → 면접 질문
```

다만 이 구조는 기계적으로 반복하는 틀이 아니라, 각 챕터에서 학습자가 다음을 이해하도록 돕는 흐름이어야 한다.

- 지금 어떤 상황을 해결하는지
- 왜 이 기술 개념이 필요한지
- 어떤 코드를 바꾸면 되는지
- 바꾼 결과가 무엇으로 검증되는지
- 면접에서는 어떤 식으로 설명해야 하는지

## 사용자의 강한 선호와 금지 패턴

사용자는 어색한 한국어, AI 티 나는 문장, 번역투를 매우 싫어한다. 다음과 같은 문장은 피해야 한다.

- 추상적인 비유로 오류를 설명하는 표현
- “타입을 잃지 않으려면?”
- “문서 배열과 금액 배열을 같은 함수로 다루면서…”
- “값은 같은데 추론된 타입은 왜 달라질까?”
- “릴리스 채널을 설정 객체에 넘겼는데…”

이런 문장은 개발자가 읽어도 무엇을 배우는지 바로 알기 어렵고, 실제 사람이 쓴 한국어처럼 보이지 않는다.

좋은 서술 방향은 다음과 같다.

- 먼저 실무에서 마주치는 상황을 말한다.
- 그 다음 학습할 개념을 연결한다.
- 예제 함수명은 중심 주제가 아니다.
- 제목은 학습 개념을 짧고 명확하게 드러낸다.
- 설명은 사용자가 “이 챕터에서 뭘 배우는지” 바로 알 수 있어야 한다.

예를 들어 `first`라는 함수명을 제목에 올리는 것은 좋지 않다.

나쁜 제목:

```text
여러 타입의 배열에 쓸 수 있는 first 함수 만들기
```

좋은 방향:

```text
제네릭 함수
제네릭 함수로 입력에 맞는 결과 타입 만들기
```

단, `Server Component 배우기`보다는 `Server Component`처럼 깔끔한 제목이 더 낫다. 실무 연결은 제목이 아니라 본문에서 반드시 설명한다.

## 커리큘럼 작성 원칙

다음 원칙은 tiny-dev-lab 전체에 적용한다.

1. 학습 주제에서 시작한다.
   - 핵심 키워드와 개념을 먼저 정한다.
   - story, 과제, 피드백, 면접 질문은 그 주제에서 확장한다.
   - 임의의 예제 상황에서 거꾸로 주제를 끼워 맞추지 않는다.

2. 실무 상황과 연결한다.
   - “이 개념이 실무에서 언제 쓰이는지”를 챕터 안에 반드시 적는다.
   - 개념을 어떤 개발 상황에서 쓰는지 설명한다.

3. 설명이 얕으면 안 된다.
   - 사용자가 설명을 읽고 해당 개념의 기본 이해를 얻어야 한다.
   - 최소한 다음을 다룬다.
     - 어떤 코드 상황에서 문제가 생기는지
     - 왜 이 개념이 필요한지
     - 흔한 실수는 무엇인지
     - 어떤 결과가 나오면 해결된 것인지

4. 과제는 설명과 직접 연결되어야 한다.
   - 과제가 본문에서 설명한 개념을 실제로 연습해야 한다.
   - 너무 쉽거나 너무 어렵지 않아야 한다.
   - 작은 문법이나 타입 작성 훈련은 한 챕터 안에 문제를 2개 이상 둬도 된다.

5. 기술 스택별 요구사항을 둘 수 있다.
   - 공통 원칙 위에 각 스택의 특수한 목표를 추가한다.
   - 예: Next.js 과정은 프로젝트 환경 세팅, 사이트 구축, 배포와 운영 확인까지 포함해야 한다.

## Next.js 과정에 대한 사용자 요구

다음 대화에서 Next.js 파트를 만든다면 반드시 다음을 반영한다.

- 완전한 작은 사이트 하나를 구축하는 흐름으로 구성한다.
- 프로젝트 환경 세팅 과정을 빼먹지 않는다.
- 페이지, 라우팅, 데이터 로딩, Server Component, Client Component, 폼, 캐싱, metadata, 배포, 운영 확인을 실무 흐름 안에서 다룬다.
- “Server Component”처럼 개념명을 제목으로 써도 된다.
- 단, 챕터 본문에는 실무에서 어떤 상황에 쓰는지 반드시 들어가야 한다.
- 배포와 운영은 선택 과제가 아니라 과정의 일부로 본다.

## 중요한 주의사항

### 2026-09-11 후속 하네스 원칙

커리큘럼 평가와 작성은 항상 대상 학습자와 수료 후 도착점에서 시작한다. 공통 과정 정의와 평가 기준은 `docs/curriculum/curriculum-quality-standard.md`에 정리했고, `scripts/verify-curriculum-quality.mjs`가 모든 스택에 다음 항목을 요구한다.

- 대상 학습자와 선수 지식
- 관찰 가능한 수료 행동
- 수료 행동까지 이어지는 단계별 순서와 이유
- 모든 공개 실습의 단계 배치와 순서
- 실습 수의 권장 범위, 근거, 평가 판정

현재 TypeScript의 36개 실습 수는 아직 평가 전이므로 `src/curriculum/course.ts`에 `pending`으로 기록했다. 콘텐츠 개선 전에 흐름, 중복, 누락, 난도와 반복 연습 필요성을 평가해 `approved` 또는 `revise`로 바꿔야 한다. 이후 기술 스택도 이 공통 하네스를 사용하고 스택별 요구만 추가한다.

- 현재 대화의 산출물을 그대로 확정본으로 취급하지 말 것.
- TS 파트는 재검토 대상이다.
- 하네스는 현재 콘텐츠를 통과시키기 위한 도구가 아니라, 콘텐츠 품질을 강제하기 위한 도구다.
- 사용자가 이해하지 못하는 제목과 설명은 실패로 봐야 한다.
- 좋은 글처럼 보이는 문장보다, 학습자가 “내가 지금 뭘 배우는지” 바로 아는 문장이 중요하다.
- gstack은 브라우저 QA/dogfooding에 쓸 수 있지만, 모든 검증을 gstack으로 해야 하는 것은 아니다. Playwright나 프로젝트 내 테스트가 더 적합하면 그쪽을 쓴다.
- Superpowers는 TDD, 계획, 스킬/하네스 구성 흐름에 유용하다. 하지만 “Superpowers가 알아서 품질을 보장한다”고 생각하면 안 된다. 품질 기준은 fixture와 실행 가능한 테스트로 고정해야 한다.
