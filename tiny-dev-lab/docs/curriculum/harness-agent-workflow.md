# 커리큘럼 하네스 에이전트 운영 방식

이 문서는 커리큘럼을 기획하고 구현할 때 어떤 작업을 별도 에이전트에 맡기고, 어떤 도구와 모델을 썼는지 남기는 기준이다. 루트 에이전트는 모든 작업을 직접 수행하지 않는다. 역할별 결과와 검증 근거를 모아 최종 판단을 내린다.

## 제품 목표

tiny-dev-lab은 wavy가 Node 풀스택 웹 개발자로 성장하는 데 필요한 기술을 결과물 중심으로 배우는 개인 학습 환경이다. 학습자는 설명만 읽는 대신 코드를 작성하고 실행 결과를 확인한다. 과정은 쉽게 시작할 수 있고, 재미를 잃지 않으며, 꾸준히 이어갈 수 있어야 한다.

[SQL Teaching](https://www.sqlteaching.com/)은 범위나 수업 길이의 기준이 아니다. 설명, 코드 입력, 실행, 실제 결과와 기대 결과를 한 흐름에서 확인하는 간결한 피드백 구조를 참고한다.

## 역할과 책임

한 작업에서 필요한 역할만 선택한다. 서로 독립적인 작업은 별도 에이전트가 병렬로 수행하고, 선행 결과가 필요한 작업은 순서대로 맡긴다.

| 역할 | 담당 작업 | 기본 산출물 |
| --- | --- | --- |
| research | 공식 문서, 도서 목차, 외부 사례 조사 | 출처와 적용 범위가 표시된 조사 기록 |
| review | 기존 기획·커리큘럼·코드의 누락과 충돌 검토 | 우선순위와 근거가 있는 검토 결과 |
| planning | 대상 학습자, 수료 행동, 학습 순서와 작업 범위 결정 | 계획서, 능력 지도, 수용 기준 |
| design | 학습 흐름, 화면, 상호작용, 피드백 방식 설계 | 사용자 흐름, 화면 명세 또는 프로토타입 |
| implementation | 승인된 범위의 문서·콘텐츠·코드 구현 | 변경 파일과 구현 요약 |
| testing | fixture, 자동 테스트, 브라우저 시나리오 작성·실행 | 재현 가능한 테스트 결과 |
| verification | 구현 결과가 계획·품질 기준·테스트를 충족하는지 독립 확인 | 통과·실패 판정과 남은 위험 |

루트 에이전트는 작업을 분해하고 파일 소유권을 배정한다. 각 결과가 서로 모순되는지 확인하고, 제품 목표와 품질 기준에 따라 최종 범위와 우선순위를 결정한다. 구현 에이전트의 자체 보고만으로 완료 처리하지 않고 검증 역할의 결과를 확인한다.

## 모델 라우팅

모델명은 설치 상태와 Codex 지원 범위에 따라 바뀔 수 있으므로 문서나 자동화에 하나의 이름을 영구 고정하지 않는다. 작업 기록에는 실제 사용한 모델과 선택 이유를 남긴다.

| capability tier | 적합한 작업 | 현재 사용할 수 있는 예 |
| --- | --- | --- |
| fast | 파일·심볼 탐색, 단순 분류, 형식 검사 | `gpt-5.6-luna` |
| standard | 구현, 테스트 작성, 범위가 정해진 검토 | `gpt-5.6-terra` |
| deep | 복잡한 구현, 설계 검토, 여러 근거의 종합 | `gpt-5.6-sol` |
| frontier | 제품 방향, 장기 구조, 충돌하는 판단의 최종 통합 | 현재 환경이 제공하는 상위 모델 |

같은 역할도 난도에 따라 다른 tier를 쓸 수 있다. 먼저 역할 프리셋이나 현재 기본 모델을 사용하고, 지원되지 않으면 다음 순서로 폴백한다.

1. 같은 역할에서 현재 환경이 지원하는 모델을 명시한다.
2. 역할 프리셋 자체가 지원되지 않으면 generic/default 에이전트에 역할, 범위, 산출물 형식을 프롬프트로 준다.
3. 저비용 모델의 결과가 불충분하면 한 단계 높은 tier로 재검토한다.
4. 폴백 사실과 이유를 작업 로그에 남긴다.

과거 `gpt-5.4`에 고정된 역할 프리셋을 호출했을 때 현재 ChatGPT Codex 실행 환경에서 지원되지 않아 에이전트 생성이 실패했다. 이 경우 실패한 프리셋을 반복 호출하거나 지원 여부를 추측하지 않는다. 현재 도구가 노출한 지원 모델 중에서 capability tier가 맞는 모델로 전환하고, 필요하면 generic/default 에이전트에 역할을 직접 명시한다.

## 플러그인·스킬·프로젝트 하네스 구분

도구의 출처를 섞어 기록하지 않는다.

- Superpowers 플러그인의 `using-superpowers`는 작업에 맞는 스킬을 먼저 고르는 데 사용한다.
- `dispatching-parallel-agents`는 독립 작업을 역할별 에이전트에 나누는 데 사용한다.
- `brainstorming`은 새로운 과정이나 상호작용을 설계할 때, `test-driven-development`는 새 규칙이나 기능을 구현할 때, `systematic-debugging`은 실패 원인을 찾을 때, `verification-before-completion`은 완료를 선언하기 전에 필요에 따라 사용한다.
- 콘텐츠 작성·검토 에이전트는 먼저 `docs/curriculum/developer-ux-writing-prompt.md`를 읽고 학습자에게 보이는 제목, 설명, 과제, 피드백과 면접 질문에 적용한다.
- `scripts/verify-curriculum-quality.mjs`, `tests/curriculum-quality.test.ts`, fixture와 프로젝트 테스트는 저장소의 실행 가능한 하네스다. 플러그인이나 스킬로 기록하지 않는다.

스킬을 사용했다고 품질이 자동으로 보장되지는 않는다. 오래 유지해야 하는 기준은 저장소의 문서, fixture와 자동 테스트로 고정한다.

## 작업 로그

기획, 구현, 검토와 검증을 수행할 때 다음 항목을 작업 문서나 인수인계에 남긴다. 사용하지 않은 항목은 `없음`으로 적는다.

```md
### 작업: <이름>

- 역할/agent: <research, review, planning, design, implementation, testing, verification>
- 실제 모델: <모델명>
- capability tier: <fast, standard, deep, frontier>
- 플러그인: <이름 또는 없음>
- 스킬: <이름 또는 없음>
- 파일 소유권: <수정 가능한 파일 또는 읽기 전용 범위>
- 산출물: <파일, 보고서, 결정>
- 검증: <명령, 검토자 판정, 미실행 사유>
- 폴백/제약: <모델·도구 실패와 대체 경로 또는 없음>
```

루트 에이전트의 최종 보고에는 역할별 결과를 어떻게 통합했는지, 해결하지 못한 충돌과 남은 위험이 무엇인지 적는다.

## 병렬 작업과 파일 소유권

- 한 파일의 편집 소유자는 한 시점에 한 에이전트만 둔다.
- 같은 자료를 읽는 것은 병렬로 할 수 있지만 같은 파일을 동시에 수정하지 않는다.
- 에이전트 프롬프트에 소유 파일, 읽기 전용 범위, 금지 범위, 기대 산출물을 구체적으로 적는다.
- 다른 에이전트의 변경을 되돌리지 않는다. 예상하지 못한 변경을 발견하면 루트 에이전트에 보고한다.
- 공유 타입이나 문서 구조처럼 여러 작업의 입력이 되는 결정은 먼저 확정한 뒤 구현을 나눈다.
- 구현과 검증은 다른 역할이 담당한다. 검증 에이전트는 구현 요약만 믿지 않고 실제 diff, 테스트 출력과 화면 결과를 확인한다.

## 현재 하네스 상태

`implemented`는 현재 실행하거나 따를 수 있는 상태, `partial`은 일부 범위만 갖춘 상태, `missing`은 아직 반복 가능한 장치가 없는 상태를 뜻한다.

| 항목 | 상태 | 현재 근거 | 다음 보강 |
| --- | --- | --- | --- |
| 공통 커리큘럼 품질 기준 | implemented | `curriculum-quality-standard.md` | 스택별 기준을 추가할 때 공통 기준과 연결 |
| 커리큘럼 구조 검사 | implemented | `scripts/verify-curriculum-quality.mjs` | 새 규칙을 fixture로 고정 |
| 하네스 자체 테스트 | implemented | 대상 학습자, 수료 행동, flow, 실습 수, helper와 stack profile 회귀 테스트가 있음 | 새 cross-stack, output, diagnostic 계약을 도입할 때 fixture 추가 |
| 전체 TypeScript 콘텐츠 검사 | implemented | 공개 레슨 40개와 진단 제외 후 정식 실습 36개의 누락 없는 검사가 구현됨 | 현재 콘텐츠 지적 23개와 `pending` 실습 수 판정 해결 |
| 개발자 UX 라이팅 기준 | implemented | `developer-ux-writing-prompt.md`와 품질 기준·운영 문서 연결 | writing/review 에이전트가 의미와 정보 구조를 독립 검토 |
| 제품 목표와 SQL Teaching 적용 원칙 | partial | 인수인계와 이 문서에 기록됨 | 전체 제품 기획과 스택별 과정 정의에 연결 |
| 역할별 에이전트 운영 | partial | 이 문서에 역할·책임을 정의함 | 실제 작업마다 배정과 결과를 로그로 남김 |
| 모델 capability tier와 폴백 | partial | 이 문서에 원칙을 정의함 | 실제 실패·전환을 작업 로그로 축적 |
| agent·모델·플러그인·스킬 로그 | missing | 공통 기록 형식만 정의됨 | 다음 작업부터 인수인계 또는 작업 문서에 작성 |
| 파일 소유권 분리 | partial | 기존 계획과 이 문서에 원칙이 있음 | 모든 병렬 작업 프롬프트에 소유 범위 명시 |
| 구현과 독립 검증의 분리 | partial | 원칙과 일부 검증 보고가 있음 | 완료 조건과 검증 담당을 매 작업에 명시 |
| 실제 학습자 관찰 | missing | 자동 검사로 대체할 수 없음 | 학습 세션 관찰과 개선 기록 마련 |

## 완료 조건

루트 에이전트는 다음을 모두 확인한 뒤 작업을 완료로 보고한다.

1. 필요한 역할별 산출물이 모였다.
2. 병렬 작업의 파일 충돌과 누락을 확인했다.
3. 구현과 독립 검증 결과가 연결되어 있다.
4. 사용한 agent, 모델, 플러그인, 스킬과 폴백이 기록되어 있다.
5. 자동 검사 결과와 사람이 판단해야 할 항목이 구분되어 있다.
6. 남은 위험과 다음 작업의 소유자가 표시되어 있다.
