## 2. 사용 목적과 완성 기준

React 개발 경험과 TypeScript 기본 문법 지식이 있으며, 제네릭·중고급 타입·실무 타입 설계를 강화하려는 개발자가 대상이다. 시간이 부족하고 영상 강의를 지속하기 어려운 상황을 고려한다. 3~7분 정도의 실습 단위로 진도를 나갈 수 있게 한다. 실제 소요 시간은 개인차가 있으므로 예상 시간으로 표시한다.

첫 버전에서도 입문 내용만 제공하고 나머지를 준비 중으로 두지 않는다. 승인된 TypeScript 커리큘럼 전체에 본문, 실습, 힌트, 검증, 해설, 출처가 있어야 완료다. 여러 기술의 빈 카드로 완성도를 부풀리지 않는다.

단순한 결과 문자열 비교만으로 통과시키지 않는다. 타입 학습 목표와 실행 시 동작을 구분하고, 학습자가 작성한 코드가 과제의 공개된 계약을 만족하는지 검증한다.

## 4. 본문과 면접 복습

공통 이야기 배경은 작은 개발팀의 제품 개선이다. 이름표, 알림, API 응답, 설정, 검색 필터 등 React 개발자가 이해하기 쉬운 상황을 활용한다. 이야기를 읽어야만 진도를 나갈 수 있을 정도로 길게 만들지 않는다.

각 수업에는 하나의 주된 목표를 둔다. 핵심 개념 설명, 수정해야 할 동작, 허용되는 입력과 출력, 검증 기준을 먼저 보여준다. 힌트는 방향 → 접근법 → 예시 해답 순으로 펼친다. 해답 열람은 완료가 아니며 코드 검증은 동일하게 수행한다.

이론에 적합한 수업에서는 결과 예측 또는 오류 진단을 사용할 수 있다. 단순히 내용을 읽었다는 버튼으로 이론 이해를 판정하지 않는다.

챕터 끝의 선택 복습은 질문, 선택적 메모, 해설 공개, 핵심 포인트 비교로 구성한다. 건너뛰어도 다음 학습을 막지 않는다. 예시 답변은 유일한 정답이 아니며, 체크 항목은 스스로 비교하는 용도다.

## 6. 최신 버전 확인 결과

2026-09-07 공식 홈페이지는 TypeScript 7.0 정식 출시를 안내한다. npm의 `typescript/latest` 응답은 7.0.2다. 구현 시작 시 다시 확인한 정확한 안정 버전을 잠금 파일과 교육 메타데이터에 기록한다. beta, rc, next는 최신 안정 버전으로 취급하지 않는다.

7.0 출시 공지는 기존 API 부재와 6.0 호환 패키지를 설명한다. 따라서 기존 JavaScript Compiler API나 브라우저 에디터의 내장 검사기가 최신 컴파일러와 동일하다고 가정하면 안 된다. 교육 검증에 오래된 컴파일러를 조용히 대신 사용하지 않는다.

각 수업은 공식 출처 URL, 확인 날짜, 검증 컴파일러 버전, 수업 개정 번호를 갖는다. 버전 업데이트는 전체 정답·오답 fixture를 재검증한 후 반영한다. 학습 중 자동으로 버전을 바꾸지 않는다.

## 7. 실행 방식 비교와 권장안

| 방식 | 이점 | 제약 |
| --- | --- | --- |
| React 화면 + 로컬 최신 컴파일러 서비스 | 최신 안정 컴파일러로 실제 검사 가능, 개인용 로컬 실행에 적합 | 웹 화면과 함께 로컬 서비스를 실행해야 함 |
| 브라우저만으로 검사·실행 | 정적 배포가 간편함 | 최신 컴파일러의 브라우저 지원 검증이 필요하며 구버전 대체를 승인 없이 할 수 없음 |
| 호스팅된 검사 서비스 | 사이트 주소로 여러 기기에서 접근 가능 | 별도 서버 운영과 격리, 이용 제한, 배포 구성이 필요함 |

사용자는 개인 전용 온라인 사이트를 선택했다. React 화면과 최신 TypeScript 검사 서비스를 호스팅하고 Supabase가 인증과 학습 기록을 담당한다. 웹 화면은 React + Vite로 빌드하고 Node 서비스가 정적 파일과 인증된 검사 API를 같은 출처에서 제공하는 구성을 제안한다. 실제 호스팅 공급자·요금제·도메인은 배포 단계에서 계정 및 가용 환경을 확인해 선택한다. 현재 특정 유료 서비스 가입이나 결제는 승인되지 않았다.

실행은 두 경계를 구분한다. 컴파일러 서비스는 고정된 수업 파일과 사용자 소스에 대해 검사·JavaScript 생성을 담당한다. 생성된 사용자 코드를 서버에서 실행하지 않는다. 실행 결과는 브라우저의 격리된 실행 환경에서 얻는다.

구현 계획에서는 브라우저 실행 환경의 네트워크·저장소 접근 차단, 부모 앱과의 메시지 검증, 실행 시간·출력량 제한, 무한 루프 중단을 필수 검증 대상으로 둔다. 단순히 Worker라는 이유만으로 보안 격리가 되었다고 간주하지 않는다.

컴파일 요청은 소스 길이, 실행 시간, 동시 요청 수를 제한한다. 클라이언트가 파일 경로, shell 명령, 컴파일러 옵션, 외부 패키지를 지정하지 못하게 한다. 로컬 서비스도 Origin과 Host를 제한하며 임시 작업 폴더 밖을 읽지 못하도록 import와 참조 경로를 통제한다.

에디터의 선택은 구현 계획에서 호환성과 번들 크기를 비교한다. 에디터의 내장 구버전 진단을 최종 결과와 혼합하지 않는다. 별도 외부 패키지 설치를 요구하는 자유 프로젝트 기능은 첫 과정에 포함하지 않는다.

## 8. 검증 계약

- 일반 실습: 구문·타입 검사 통과와 동작 테스트 통과를 함께 요구한다.
- 타입 전용 실습: 허용해야 할 값과 거절해야 할 값을 모두 검사한다.
- 오류 관찰 수업: 수업이 명시한 예상 오류와 예측 답변을 확인한다. 오류가 존재한다는 이유만으로 실패 처리하지 않는다.
- 코드 문자열 일치나 정규식만으로 정답을 판정하지 않는다. 여러 올바른 구현을 허용한다.
- `any` 또는 오류 억제로 과제를 우회하는 답안은 학습 목표에 따라 검증한다. AST 제한만으로 타입 안전성을 증명했다고 간주하지 않는다.
- 정답, 대체 정답, 대표 오답, 경계값, 빈 코드에 대한 fixture를 둔다.
- 오래된 실행 결과가 다른 수업이나 수정된 코드의 완료 상태를 바꾸지 않도록 요청 ID, 수업 ID, 코드 개정을 연결한다.
- 완료 기록은 성공한 코드 개정과 수업 개정을 저장한다. 이후 수정한 코드는 재검증 전임을 표시하며 과거 완료 이력을 잃지 않는다.

## 9. 인증과 저장 — 개인 전용 Supabase 동기화

2026-09-08 사용자가 개인 전용 온라인 사용과 Supabase 동기화를 선택했다.

인증은 Supabase 기본 이메일 Magic Link다. 회원가입은 닫고 Supabase에 등록한 소유자 계정만 허용한다. 화면을 숨기는 것만으로 접근을 막지 않는다. API는 Supabase가 발급한 토큰의 서명·만료·발급자·대상과 소유자 ID를 검사하며, 다른 유효한 Supabase 사용자도 거부한다. 브라우저에는 공개용 키만 두고 service-role 키는 포함하지 않는다.

데이터는 사용자 ID, 수업 ID, 콘텐츠 개정, 코드 초안, 초안 개정, 성공한 코드 개정, 완료 시점, 선택 복습 메모를 갖는다. 마지막 방문 수업도 저장한다. 모든 사용자 데이터에 RLS를 적용하고 읽기·쓰기·삭제 모두 소유자로 제한한다.

로그인 상태에서 코드 변경을 잠시 모아 자동 저장한다. 저장 중·저장됨·오프라인·충돌 상태를 표시한다. 연결이 끊기면 해당 기기에 임시 초안을 보관하고, 다시 연결되면 서버 개정을 비교한다. 다른 기기에서 변경한 경우 자동 덮어쓰기하지 않고 두 버전을 보존해 선택하게 한다. 최신 수정 시각만으로 충돌을 해결하지 않는다.

로그아웃 시 화면의 코드·메모를 비우고 서버 기록은 유지한다. 동기화하지 못한 초안이 있으면 저장하거나 내보낼 수 있도록 안내한 뒤 로그아웃한다. 토큰 만료나 저장 실패를 학습 과제 오답으로 표시하지 않는다.

Supabase 계정·프로젝트와 소유자 이메일은 아직 제공되지 않았다. 로컬 개발과 검증에는 환경변수 템플릿 및 인증 테스트를 사용할 수 있지만, 실제 로그인·동기화 검증과 배포 완료를 주장하려면 실제 연결 검증이 필요하다. 비밀키를 채팅으로 요청하지 않는다.

3. 최신 컴파일러 검사와 격리 실행을 먼저 검증한다. 불가능한 경우 구버전으로 바꾸기 전에 사용자에게 제약과 대안을 제시한다.
4. 하위 모델 에이전트가 UI, 교육 콘텐츠, 검사·실행 모듈을 분담한다. 공유 타입과 계약은 먼저 고정한다.
5. 실제 첫 실습부터 마지막 실습까지 모든 콘텐츠와 검증을 통합한다.
6. 타입 검사, lint, 검증 fixture, 학습 이동·저장·복구·완료·오류 상태 테스트를 실행한다.
7. 데스크톱과 모바일에서 실제 화면과 키보드 동작을 확인한다. 시각 변경 시 visual-verdict 검토 기록을 남긴다.

## 13. 커리큘럼 — 기본 문법에 익숙한 개발자를 위한 재설계

### 13.1 대상과 기존 구성의 문제

2026-09-08 추가 요구: 사용자는 TypeScript 기본 문법에 이미 익숙하다. 부족한 영역은 제네릭, 중고급 문법, 실제 프로젝트 상황에 맞는 타입 설계다. 기본 문법을 처음부터 순서대로 반복하는 과정으로 만들지 않는다.

기존 36개 수업의 앞 17개(약 47%)가 기본 문법과 좁히기에 집중되어 있었다. 제네릭을 직접 다루는 수업은 21~22번의 2개뿐이었다. 마지막 4개 수업에는 React·JSX, 비동기 응답, 선언 파일, 서버 경계, 오류 해결이 과밀하게 배치되었다. 또한 React·JSX 실습을 넣으면서 React 패키지 없이 진행한다는 설명을 그대로 둔 모순이 있었다.

개정안은 선택 진단 4개와 본과정 36개로 구성한다. 본과정의 16개는 제네릭·타입 변환을 실무 예제로 배우고, 나머지 20개는 도메인 모델·React·프로젝트 통합·종합 과제에 적용한다. 이는 수업 수의 배분이며 실제 시간 비율은 아니다. 36이라는 숫자를 맞추기 위해 어려운 개념을 한 페이지에 몰아넣지 않는다. 집필 시 3~7분의 한 목표로 소화되지 않는 항목은 과정을 줄이지 않고 실습을 분할한다.

### 13.3 수업별 주된 목표

선택 진단:
- D1. 값은 같은데 추론된 타입은 왜 달라질까? — const/let과 리터럴 넓어짐.
- D2. 유니온의 필드를 바로 읽을 수 있을까? — 분기와 좁히기.
- D3. as를 붙이면 외부 데이터도 안전해질까? — unknown, any, 타입 소거.
- D4. 속성이 더 있는 객체는 언제 허용될까? — 구조적 호환성과 초과 속성 검사.

1장 — 제네릭:
1. 목록의 첫 항목을 꺼내도 원래 타입 유지하기 — T의 입력·출력 관계; 빈 목록은 undefined로 표현.
2. 호출할 때마다 타입 인자를 써야 할까? — 타입 인자 추론과 명시의 선택.
3. 목록을 변환하면 결과 타입도 바뀐다 — T와 U를 콜백으로 연결.
4. 아무 객체나 받으면 id를 읽을 수 없다 — extends 제약과 실제로 보장되는 범위.
5. 존재하는 필드만 선택하기 — K extends keyof T를 도입.
6. 고른 필드에 맞는 값 타입 돌려주기 — T[K]로 키·값의 관계 보존.
7. 페이지 응답 타입 재사용하기 — 제네릭 타입 별칭과 기본 타입 인자.
8. 이 함수에는 제네릭이 정말 필요할까? — 유니온·오버로드·제네릭의 대안 비교; 값들의 관계가 없는 타입 인자는 제거.

2장 — 타입 변환:
9. 설정을 검사하면서 리터럴 정보 보존하기 — typeof, as const, satisfies의 역할 비교.
10. 수정 요청에서 바꿀 수 있는 필드만 고르기 — Pick/Omit/Partial 조합의 목적과 한계.
11. 모델의 각 필드를 폼 오류로 바꾸기 — mapped type의 순회와 선택 modifier.
12. 공개할 키만 남기거나 이름 바꾸기 — key remapping.
13. 입력 타입에 따라 결과 타입 선택하기 — conditional type의 분기.
14. 함수 타입에서 필요한 부분 꺼내기 — infer; Parameters/ReturnType과 연결.
15. 유니온을 넣었더니 결과가 여러 개가 됐다 — 분산 조건부 타입과 분산 억제 비교.
16. 이벤트 이름의 오타 막기 — template literal type으로 이벤트 이름 유니온 생성; 타입 조합의 크기 주의.

3장 — 도메인과 경계:
17. loading인데 data가 있는 상태 막기 — 판별 유니온과 never 완전성 검사.
18. 내가 만든 타입 가드를 믿어도 될까? — 타입 술어가 잘못 약속하는 반례; assertion function과의 비교는 짧은 해설로 제공.
19. 외부 응답은 unknown에서 시작하기 — 작은 객체의 런타임 검사와 안전한 변환; fetch<T> 표기만으로 검증되지 않음을 확인.
20. 서버 DTO를 화면 모델과 분리하기 — 날짜 문자열·nullable 값의 명시적 변환.
21. 비동기 성공과 실패를 반환 타입에 담기 — Promise<Result<T, E>>, Awaited; throw된 오류까지 자동으로 타입화되는 것은 아님.
22. 사용자 ID와 주문 ID를 바꿔 넣지 않기 — branded type과 검증된 생성 경계; 런타임 검증을 대신하지 않음.

4장 — React에 적용:
23. 기존 버튼의 props를 재사용하기 — ComponentProps와 충돌하는 속성의 Omit; children/ReactNode는 참고 해설.
24. props를 각각 optional로 만들면 생기는 문제 — 모드별 props 조합을 판별 유니온으로 제한.
25. 사용자 목록과 주문 목록을 같은 컴포넌트로 — 제네릭 목록의 items와 renderItem 타입 연결.
26. 입력 이벤트에 any를 붙이지 않기 — 이벤트 타입과 currentTarget; 폼 값의 문자열 경계 확인.
27. action마다 다른 payload 안전하게 처리하기 — reducer의 State·Action 계약과 완전성.
28. Context의 null을 곳곳에서 단언하지 않기 — Provider 존재를 확인하는 소비 Hook의 반환 타입.

5장 — 프로젝트 통합:
29. 라이브러리의 복잡한 타입부터 읽기 — 제공 타입 재사용 및 콜백 매개변수 호환성 오류 추적; variance는 해당 반례로 설명.
30. 누락된 타입을 any로 덮지 않기 — 작은 .d.ts 또는 module augmentation 과제; 근거 없는 선언은 검증이 아님.
31. 타입만 가져왔는데 런타임 import가 남았다 — import type과 verbatimModuleSyntax를 주어진 다중 파일 fixture에서 진단; ESM/CJS 전체 상호운용과 lib/types 환경 분리는 연결된 참고 설명으로 제공.
32. 필드가 없다는 것과 undefined를 넣는 것은 같을까? — exactOptionalPropertyTypes를 수정 요청 사례로 비교; noUncheckedIndexedAccess는 1번·5번에 적용한 설정을 되짚기.

6장 — 동일한 작은 기능을 연결하는 종합 실습:
33. 잘못된 API 응답을 앱 안으로 들이지 않기 — 제공된 프로젝트에서 외부 응답 검증 부분 완성.
34. 읽기 모델과 수정 요청 구분하기 — 서버가 정하는 필드와 사용자가 바꿀 필드 분리.
35. 모델에 맞는 재사용 목록 연결하기 — 제공된 TSX 화면의 제네릭 props와 콜백 완성.
36. 요구사항이 바뀌어도 계약 유지하기 — API 필드 변경에 따른 타입 오류를 추적하고 정상·오류 입력 회귀 검증 통과.

종합 과제는 백지에서 앱 전체를 만드는 과제가 아니다. 같은 작은 프로젝트의 제공된 코드에서 한 부분씩 완성한다. 수업 간 작성 코드와 완료 기록을 보존하며, 종합 실습에서 새로운 고급 문법을 갑자기 요구하지 않는다.

### 13.4 깊이와 학습 방식

모든 본과정 수업에 업무 상황을 넣는다. 먼저 필요한 동작을 제시하고, 타입 관계를 설계하고, 여러 올바른 호출과 거절할 호출로 확인한다. 제네릭 수업을 identity<T> 예제만으로 끝내거나 고급 타입을 문법 암기로 평가하지 않는다.

코드를 읽고 결과 타입을 예측하기 → 일부 수정하기 → 작은 계약 직접 작성하기 → 요구사항 변경하기 순서로 발판을 줄인다. 주된 개념을 처음 도입하는 수업에서는 관련 없는 구현 코드를 제공한다.

핵심 이론은 별도 긴 이론 장으로 격리하지 않고 관련 실습에 연결한다: 타입 소거와 런타임 경계(D3·19), 구조적 타입과 비건전성(D4·18), 추론과 제약(1~8), 분산 조건부 타입(15), 함수 매개변수 호환성(29). 재귀 타입·variadic tuple·고급 polymorphic 컴포넌트·명시적 variance annotation은 연결된 공식 문서와 심화 해설로 제공하며 첫 본과정의 필수 구현 과제로 늘리지 않는다.

React 수업은 공식 React 타입 정의와 고정된 TSX fixture를 제공해 검사한다. 사용자가 패키지를 설치하거나 React 실행 방식을 새로 배울 필요는 없다. 필요한 런타임·타입 정의는 서비스가 검증한 버전으로 사전 제공한다. JSX 실행 및 렌더링 과제에 필요한 지원은 구현 계획의 실행기 범위에 포함한다. useState의 nullable 추론과 useRef의 DOM 타입은 React 장의 필요 시 펼치는 복습 예제로 제공한다. React의 Hooks 동작 원리·RSC·SSR 자체는 다음 React 과정에서 다룬다.

strict는 전 수업에 명시적으로 적용한다. noUncheckedIndexedAccess를 기본으로 사용하고 첫 목록·필드 조회 과제에서 부재 가능성을 설명한다. exactOptionalPropertyTypes는 32번에서 설정 전후를 비교하며, 설정을 바꿔 오류를 숨기는 방식으로 통과시키지 않는다. 네트워크·시간·난수는 고정 fixture로 대체한다.

검토 기준: 선택 진단 4개와 본과정 36개를 구분한다. 제네릭은 2개에서 8개로 확대하고 실무 적용을 전 장에 배치했다. React·서버·모듈을 마지막 한 수업에 합치지 않는다. 학습자 수준, 실행기 요구, 완료 기준은 본문과 함께 검토한다. 이 개정은 커리큘럼 설계 변경이며 앱 구현 착수나 최종 설계 전체의 승인을 의미하지 않는다.



## 14. 구현 전 확정 사항 (2026-09-08)

사용자는 개정된 13번을 승인했다. Supabase 프로젝트는 아직 없으며 연결은 구현 후 진행한다고 명시했다. 현재 로컬 구현·검증을 진행하고 온라인 연결은 준비 파일을 완성한 뒤 별도로 검증한다. React 타입 실습의 미리보기는 격리 Worker에서 실제 React가 생성한 정적 HTML이며, 이벤트와 reducer는 순수 함수 계약으로 검사한다. React 동작 교육을 위한 자유로운 DOM 상호작용 미리보기는 이번 TypeScript 과정의 목표가 아니다.
