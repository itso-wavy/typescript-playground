# TS 실험 커리큘럼 평가

평가일: 2026-09-11. 대상: 현재 작업 트리의 진단 4개와 실습 36개.

후속 상태: 같은 날 검사 도구를 수정했다. 아래 평가는 수정 전의 기록이다. 전수 수집, c34 검증 보강, 공식 URL 판정의 수정 결과는 [검증 기록](../verification.md)의 `2026-09-11 검사 도구 수정`을 참고한다. 콘텐츠의 23건 지적과 교육 설계 개선 사항은 남아 있다.

## 결론

현재 과정은 실행 가능한 실습 초안이다. 최종 커리큘럼이나 다른 스택의 작성 기준으로 확정하기에는 부족하다. 특히 품질 하네스가 실습 20개를 누락하고 있어, 요약 11개만 보완하면 끝나는 상태가 아니다.

평가 기준은 `docs/handoffs/2026-09-11-ts-bottom-up-harness-handoff.md`의 작성 원칙이다. 기존 acceptance matrix는 과거 평가 자료로 참고하고 현재 코드와 대조했다. 현재 콘텐츠에 맞춰 하네스의 기준을 낮추지 않았다.

## 이번 실행에서 확인한 증거

| 검사 | 결과 | 해석 |
| --- | --- | --- |
| `npm.cmd run test:curriculum-quality` | 실패 11건: g02~g06, t10~t13, t15~t16 요약 | t14는 현재 실패하지 않는다. |
| `npm.cmd test -- tests/curriculum-quality.test.ts` | 3/3 통과 | 좋은 fixture, 필수 단계 누락, 예제명 제목의 세 시나리오만 증명한다. |
| 전체 레슨을 같은 품질 규칙에 전달 | 23건 실패 | 요약 21건, 실무 상황 단어 2건. 수집 누락을 우회했으며 규칙은 변경하지 않았다. |
| `npm.cmd run test:curriculum` | 타입·브라우저 두 단계 통과 | 런타임 대상 26개, 정상 후보 52개 통과, 타입 단계 거절 21개, 런타임 단계 거절 7개, 실패 0건. |

전체 레슨 검사는 기존 esbuild의 `transform`으로 7개 콘텐츠 모듈을 메모리에서 읽고, 실제 내보낸 lessons 40개를 임시 JSON fixture로 만들어 기존 `--fixture` 명령에 전달했다. starter/solution 존재 여부도 fixture 형식에 맞춰 전달했다. 앱이나 하네스 소스는 수정하지 않았다. 첫 bundle 시도는 상위 디렉터리 접근 제한으로 실패하여 파일별 transform으로 전환했다.

## 우선 해결할 문제

### P1. 품질 하네스가 후반부 실습 20개를 검사하지 않는다

`scripts/verify-curriculum-quality.mjs:123`은 배열 원소가 `ObjectExpression`일 때만 레슨으로 수집한다. boundaries/react의 `lesson({...})`, integration/capstone의 `make({...})`는 호출 표현식이므로 빠진다. 수집되는 20개 중 진단 4개도 149행에서 제외되어 실제 공통 품질 검사 대상은 실습 16/36개다.

누락된 구간까지 포함하면 요약 실패는 다음 21개다.

- g02, g03, g04, g05, g06
- t10, t11, t12, t13, t15, t16
- b17, b19, b20, b22
- r24, r26, r27
- p32, c33, c36

r24와 p29에는 상황 단어 오류도 추가된다. r24는 실제로 링크 버튼과 href 문제를 설명하므로 이 오류를 곧바로 실무성 부족으로 판정하면 안 된다. p29는 호출자와 Row의 추상 설명에 치우쳐 어떤 라이브러리 사용 상황인지 보강할 여지가 있다. 정규식 결과와 편집 판단은 구분해야 한다.

개선 완료 조건: 공개 레슨 ID 집합과 품질 검사의 수집 ID 집합을 대조하고, helper로 작성된 레슨의 결함도 실패하는 회귀 fixture를 둔다. 해석하지 못한 배열 원소는 조용히 건너뛰지 않아야 한다. 진단 제외 정책과 검사 수를 결과에 명시한다.

### P1. 과제의 목표를 지키지 않은 코드도 검사에 합격할 수 있다

c34의 본문은 quantity의 정수·범위 검증을 요구한다. 하지만 `server/curriculum/capstone.ts`의 runtimeTests는 잘못된 수량으로 -1만 검사한다. 음수만 거절하는 함수가 네 검사에 모두 통과하면서 1.5와 NaN을 허용했다. 이 재현은 해당 런타임 fixture의 부족을 증명하며, 변형 코드에 대한 전체 checkLesson 경로까지 실행한 결과는 아니다.

개선 완료 조건: 정상 0과 양의 정수, 음수, 소수, NaN, Infinity, undefined 생략을 검사하고 정수 검증만 빠진 그럴듯한 오답을 추가한다. 다른 레슨에도 목표별로 어떤 실패 입력이 그 목표를 검증하는지 연결해야 한다.

### P1. 입문 안내와 실제 진입 난도가 맞지 않는다

`src/learning/TypeScriptIntro.tsx`는 처음에 변수와 함수에 타입을 붙인다고 설명하지만 정식 실습은 바로 g01 제네릭 함수로 시작한다. 진단은 기초를 가르치는 단계를 대신하지 않는다. t12는 템플릿 리터럴 타입과 Extract를 이미 사용하지만 해당 주제의 별도 레슨은 t16에 있다. c35는 오버로드를 새 핵심 주제로 도입한다.

개선 완료 조건: JavaScript와 기본 TypeScript를 아는 학습자용 과정인지 먼저 명시하고 소개 문구를 맞춘다. 기초 과정으로 삼으려면 선수 학습을 제공한다. 레슨별 선수 지식과 새 개념을 구분하고, 캡스톤에 앞서 배우지 않은 핵심 문법을 넣지 않는다.

### P2. 제목이 약속한 학습 행동을 starter가 이미 제공한다

- t11은 매핑된 타입의 기본 문법 작성을 목표로 하지만 starter에 `[K in keyof T]`가 완성되어 있다. 실제 변화는 `?` 한 글자다.
- b21은 Result 타입이 starter에 완성되어 있어 실제 과제는 숫자 검증과 성공/실패 객체 반환이다. 호출자가 두 결과를 처리하는 행동은 직접 연습하지 않는다.
- c35는 오버로드 설계를 제목으로 내세우지만 두 overload signature가 starter에 완성되어 있다. 학습자가 작성하는 것은 구현 분기다.

작은 수정 자체는 문제가 아니다. 다만 목표를 그 수정에 맞추거나, 짧은 추가 과제로 다른 모델·호출부에서도 개념을 적용하는지 확인해야 한다. 힌트를 따라 정답 문법을 복사하는 것과 이해를 구분할 증거가 필요하다.

### P2. 요약 분량을 늘리는 것만으로 설명 깊이는 해결되지 않는다

g06의 설명은 T[K]를 정의하지만 잘못된 반환 타입과 정확한 반환 타입을 호출부에서 비교하는 예가 부족하다. t15는 분산 규칙을 설명하지만 혼합 유니온을 넣었을 때 두 결과가 어떻게 달라지는지 본문에서 직접 보여주지 않는다. g01에는 “함수 이름이 아니라”라는 내부 편집 논의가 학습 본문과 통과 설명에 남아 있다.

개선 완료 조건: 문제 코드 → 필요한 개념 → 흔한 오답 → 관찰할 결과를 설명 안에 넣는다. 45자 기준 충족은 최소 형식 조건으로 유지하되 의미 없는 문장 추가로 해결하지 않는다.

### P2. 면접 질문의 역할과 보장 범위가 불분명하다

현재 질문은 d4, g08, t16, b21, b22, r28, p32, c36의 8개에 있다. 실습 기준으로는 7/36개이며 각 정식 장의 마지막 레슨에는 질문이 있다. UI도 이를 “챕터 복습 · 선택”으로 표시한다. 따라서 질문이 모든 레슨에 없다는 이유만으로 일괄 결함으로 보지는 않는다.

다만 인수인계의 학습 흐름과 어떤 단위로 연결할지 확정되지 않았다. 현재 하네스는 interview를 읽거나 정합성을 검사하지 않는다. t16의 질문 불일치는 이미 수정되었지만 같은 문제가 다시 생겨도 이 하네스는 잡지 못한다.

개선 완료 조건: 장별 복습인지 레슨별 질문인지 명시하고, 질문·답·평가 관점이 직전 과제의 코드 선택과 한계를 묻는지 검토한다. 질문 유무와 필수 필드는 자동 검사하고 의미 정렬은 별도 편집 검토로 남긴다.

### P2. 공식 도메인 존재만으로 출처 적합성을 보장하지 못한다

integration의 네 레슨은 TSConfig 첫 페이지를 공유하고 capstone은 모두 narrowing 페이지를 공유한다. c35 오버로드 등은 주제에 직접 대응하는 절이 필요하다. 현재 공식 URL 판정도 `url.includes(domain)`이라 도메인 문자열이 경로나 쿼리에만 있어도 통과할 수 있다.

개선 완료 조건: URL의 hostname을 검증하고, 레슨별 공식 문서의 관련 절을 지정한다. 문서 내용과 설명의 기술적 일치는 별도 검토한다. 이번 평가는 로컬에 기록된 링크의 배치와 검사 로직을 확인했으며 외부 페이지의 최신 내용·접속 가능성은 검증하지 않았다.

### P2. 기존 평가표를 현재 설계로 사용하면 잘못된 수정을 하게 된다

`typescript-acceptance-matrix.md`와 현재 콘텐츠의 차이:

| 항목 | 현재 확인 | 판단 |
| --- | --- | --- |
| t16 인터뷰 불일치 | 이벤트 이름 갱신과 조합 비용 질문으로 수정됨 | 과거 결함은 해소. 요약 보강은 남음. |
| b18 주소 중심 제목 | 사용자 정의 타입 가드로 수정됨 | 제목 문제 해소. |
| b21 async 혼합 | 동기 parseQuantity와 인터뷰로 수정됨 | 범위 축소 반영. 호출부 연습은 남음. |
| p29/p30 | 핵심 용어 및 선언 파일 한계 설명 보강됨 | 일부 반영. 한국어와 출처는 재검토. |
| c34 반복 과제 | 생략과 수량 검증으로 구별됨 | 목표 차별화 반영. 검사 누락은 남음. |
| c35 주문 목록 | 현재는 주문 표시 함수 오버로드 | 내용·선수 지식·관찰 행동을 다시 평가해야 함. |

이 표는 완성된 기획을 대체하지 않는다. 이전 acceptance 문서의 예제명 중심 navTitle 권고 등은 이후 handoff 원칙보다 우선할 수 없다.

## 유지할 장점

- API 검증, 수정 요청의 생략/null, React props, Provider 누락처럼 실무 문제와 연결된 소재가 있다.
- 정상 해답 외에 대안 구현과 오답을 타입·실행 단계로 나눠 검사하는 기반이 있다.
- b18/b19/b22 등은 타입 선언과 실제 값 검증의 차이를 설명한다.
- t16과 b21은 이전 피드백을 반영한 개선이 확인된다.
- 캡스톤의 starter는 독립 실행에 필요한 파일을 제공한다.

## 다음 작업 순서

1. 공개 레슨 전수 수집과 수집 누락 실패를 테스트로 고정한다.
2. c34처럼 목표와 검사 사이의 빈틈을 오답 fixture로 고정한다.
3. 대상 학습자, 선수 지식, 장별 도달 행동, 면접 질문 단위를 탑다운으로 확정한다.
4. 설명·과제·출처를 함께 고친다. t11/b21/c35는 제목과 실제 작성 행동을 맞춘다.
5. 기존 acceptance matrix를 현재 목표와 코드에 맞춰 갱신하고, 같은 기준으로 새 스택 설계에 들어간다.

## 변경 범위와 남은 검증

이번 변경은 이 평가 문서 추가뿐이다. 코드 단순화나 하네스 완화는 하지 않았다. 기존 작업 트리의 수정 사항은 유지했다. 코드 변경이 없어 lint/typecheck/build 전체를 다시 돌리지는 않았고, 평가에 필요한 품질 검사와 전체 커리큘럼 검사를 실행했다. 실제 학습자 관찰, 전체 UI 카피의 화면 검토, 외부 공식 문서 최신성 검증은 남아 있다. 위 개선 사항은 아직 구현되지 않았다.
